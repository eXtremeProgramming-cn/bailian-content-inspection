Content inspection on Alibaba Cloud Model Studio

A close reading of the official documentation: what the X-DashScope-DataInspection request header configures, which values it accepts, what each value means, and how to read the DataInspectionFailed error.

About this page

This is an independent reading of Alibaba Cloud's official documentation about content inspection on Model Studio (DashScope, also known as 百炼 / Bailian). Agent-style workloads — long prompts, retrieved documents, research material — occasionally trip the platform's content inspection on legitimate input, and the resulting error is confusing if you have never seen it. This page collects, in one place and with links to the official sources, what the platform documents about that mechanism and its configuration.

Every factual claim here links to an official Alibaba Cloud page, listed under References (all accessed 2026-09-20). Where official documents are incomplete or silent, that status is stated plainly rather than papered over.

Two layers of content checking

Model Studio applies content checks at two layers, and it is worth keeping them apart because they fail differently:

  • The model layer. Each model carries its own compliance behavior. When it declines a request, the HTTP call typically succeeds (HTTP 200) and the response body contains a refusal. This layer is a property of the model and is not configured by the header on this page.
  • The platform layer. A content-security screening runs in front of the model. When it intercepts, the call fails with HTTP 400 and an error code of DataInspectionFailed (DashScope-native protocol) or data_inspection_failed (OpenAI-compatible mode). This is the layer the X-DashScope-DataInspection header configures.

The error you may see

On the Anthropic-protocol endpoints the error surfaces as:

server error: <400> InternalError.Algo.DataInspectionFailed: Input text data may contain inappropriate content.

On the OpenAI-compatible endpoint the same failure looks like:

Error code: 400 - {
    "error": {
        "message": "Input data may contain inappropriate content.",
        "type": "data_inspection_failed",
        "code": "data_inspection_failed"
    }
}

The official error-code reference lists the family under 400-DataInspectionFailed / data_inspection_failed with the messages “Input or output data may contain inappropriate content.”, “Input data may contain inappropriate content.” and “Output data may contain inappropriate content.”, and states the cause: the input or output was intercepted by the content-security layer as suspected sensitive content. The reference's listed remedy is to modify the input and retry. Related documented codes include 400-CustomRoleBlocked (blocked by a custom rule) and a pre-inference image check for multimodal input. The content-security page additionally notes that in retrieval-augmented (knowledge-base) scenarios, text retrieved from uploaded documents is injected into the model input and can trigger the same interception.

Two things follow from reading these pages together. First, the error is about the platform layer: nothing in it says the model was asked and refused — the request was stopped in front of the model. Second, when the flagged text is retrieved material or an agent's assembled context rather than something the user typed, “modify the input and retry” is not actionable advice, because the content is legitimate and the wording is not really under your control. That is the case the configuration below addresses.

The X-DashScope-DataInspection header

The header is set on API requests as a JSON string, for example: -H "X-DashScope-DataInspection: {\"input\": \"cip\", \"output\": \"cip\"}". The input and output members configure inspection of the request and of the response, respectively. The values that appear in official documentation and official example code:

ValueWhat it meansOfficial source
{"input":"cip","output":"cip"} Routes the request's input and output through the AI Guardrail (安全护栏), a value-added service: it is activated and authorized separately in the console, billed per token, supports configurable policy tags, and logs inspectable results. Requests that fail the guardrail return the 400 error above. Text API reference, Content-security page
(header not set) For Qwen text models, the reference describes the default as no additional inspection beyond the model's own. Note, however, that platform-side screening is observed to run by default in some configurations — notably realtime speech interfaces and hosted third-party models — which is precisely where the error above tends to appear. Text API reference
{"input":"disable","output":"disable"}
(flat form disable / enable also exists)		 Turns the platform-side inspection off for the request, separately for input and output. Alibaba's own example code for the realtime speech interface passes "x-dashscope-dataInspection": "disable" for this purpose. Realtime speech guide (official example code)

Documentation status, stated plainly. The main text-API reference documents only the cip form and the unset default. The disable value appears in writing in Alibaba's realtime-speech example code, and the gateway accepts the same header on the text endpoints (verified 2026-09-20 against both the OpenAI-compatible and Anthropic-compatible endpoints on dashscope.aliyuncs.com, where the header is accepted and unknown headers are ignored). Production use indicates it suppresses the platform-side inspection that produces DataInspectionFailed on hosted third-party text models. Since it is a per-request header, it can also be enabled selectively — only for the clients and tasks that need it — rather than as an account-wide posture.

Setting the header in common clients

Back up before you edit. Before modifying a configuration file — settings.yaml, .claude/settings.json, or similar — make a backup copy of it first, in the same folder (for example settings.yaml.bak-20260920-1530). If an edit goes wrong, copying the backup back over the original file undoes it.

The header is ordinary HTTP and can be set anywhere custom request headers are supported. Examples:

curl (OpenAI-compatible endpoint)

curl -X POST https://dashscope.aliyuncs.com/compatible-mode/v1/chat/completions \
  -H "Authorization: Bearer $DASHSCOPE_API_KEY" \
  -H "Content-Type: application/json" \
  -H 'X-DashScope-DataInspection: {"input": "disable", "output": "disable"}' \
  -d '{"model": "...", "messages": [...]}'

OpenAI SDK (Python)

completion = client.chat.completions.create(
    model="...",
    messages=messages,
    extra_headers={
        "X-DashScope-DataInspection": '{"input": "disable", "output": "disable"}'
    },
)

Anthropic-protocol clients (e.g. Claude Code)

Claude Code exposes custom request headers through the ANTHROPIC_CUSTOM_HEADERS environment variable, which can be set in the project's .claude/settings.json or settings.local.json under env:

{
  "env": {
    "ANTHROPIC_CUSTOM_HEADERS": "X-DashScope-DataInspection: {\"input\":\"disable\",\"output\":\"disable\"}"
  }
}

DeepSeek Harness (DSH)

DSH provider routes accept a headers map in settings.yaml, next to apiKeyEnv and baseURL. In YAML, quote the value so it stays a string:

llm-pi-ai:
  providers:
    my-provider:
      headers:
        X-DashScope-DataInspection: '{"input":"disable","output":"disable"}'

The adapters re-read the file on the next request; no restart is needed.

Boundaries, and the official alternatives

  • What switching this header off does not do. It configures only the platform layer. The model's own compliance behavior is unaffected: content the model itself declines will still be declined, as an in-response refusal rather than a 400. Turning off platform-side inspection reduces false positives on legitimate material; it is not an all-clear for any content.
  • Compliance-sensitive deployments. If your use of the platform carries regulatory or organizational content obligations (enterprise, publishing, education at scale), evaluate whether and how to configure inspection before changing it. The guardrail route exists precisely for deployments that need inspection with finer-grained, self-managed policy tags.
  • Official alternatives for false positives. Alibaba documents a whitelisting process (内容加白): submitting a support ticket with the full error and the scenario, after which reviewed content is added to an exemption list. For recurring false positives on a stable corpus, that is the vendor-supported path; the header is the immediate, per-request path.
